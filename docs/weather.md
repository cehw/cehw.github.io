# Hong Kong weather

The standalone **Weather** page (`weather.html`) contains the **Local weather prediction playground**, with Hong Kong Observatory local and daily forecasts and a map that switches between station observations and experimental six-hour GNN forecasts. Like Gallery, it uses the shared navigation, background, width, fonts and themes. At the user's request, the homepage also shows a compact Clear Water Bay current-weather estimate and a link to the playground. This uses the existing Open-Meteo request at 22.336°N, 114.265°E, not an HKO station observation. The source is credited beside the link; the displayed time is the API data time in HKT. Requests refresh every 15 minutes while visible. Missing readings produce an unavailable state; readings over one hour old are marked delayed. Background preview overrides are visibly labeled Preview. The full HKO and GNN dashboard remains on the standalone page. Legacy `index.html#weather` links redirect to the dedicated page, preserving query parameters.

The introduction cites our related GNN study: Wang, H., Tang, J., Zhang, J., and Yang, J. (2026), *Intra-city scale graph neural networks enhance short-term air temperature forecasting*, Atmospheric Chemistry and Physics, 26, 947–961, [doi:10.5194/acp-26-947-2026](https://doi.org/10.5194/acp-26-947-2026). This is a research reference; the deployed experimental CLP model is described below.

## Observation-only GNN

The user selected **no Aurora**. The service now supports 39 temperature, 26 humidity and 30 wind stations across 53 distinct physical sites. Original-node forecasts retain the existing CLP pilot; a separately fine-tuned 53-node GNN supplies the new sites. See [Weather model](weather-model.md) for architecture, chronological training periods, backtest results and the temperature limitation. Parameters and raw data are private server/local artifacts; only predictions, provenance and concise evaluation information are published.

Inputs are 72 hours of ten-minute HKO temperature, humidity, pressure, wind speed, compass direction and gusts, with the original missing-value masks. Native output spans 24 hours; this website publishes only the first 36 ten-minute leads (six hours). Wind direction is not published. Humidity is clipped to 0–100% and speed to nonnegative values. Missing or unsupported target variables remain absent.

The map uses each variable's available physical station set. TY1/SHL, TU1/TUN and STY/BHD remain distinct temperature/humidity and wind sites. HKO and YCT have no substituted wind forecast. Current observation gaps can temporarily reduce published station counts. The page opens on the GNN layer by default and automatically plays the remaining forecast leads at 1.2 seconds per ten-minute step, looping back to the first future valid time. Play/Pause is explicit; dragging the slider, choosing an hourly value, using the station selector or opening a station popup pauses playback. Hidden tabs suspend the timer and resume only if playback was active. Unavailable or expired forecasts do not animate. The slider selects any ten-minute lead; each selected station also offers six hourly values. The GNN note identifies it as an experimental playground for exploring local weather predictions; HKO receives credit for input observations, and the separate HKO panels remain explicitly labeled.

A fixed 00:00–24:00 HKT day/night timeline shares one compact card with Forecast time, the forecast slider and Play/Pause. For available forecasts, issue and origin timestamps appear as one compact line inside this card; the separate availability banner is omitted. Unavailable, expired and warming-up forecasts retain the status explanation. Temperature, Humidity and Wind are direct-choice buttons in the Forecast time header alongside Play/Pause; the selected variable remains visible and switching retains the current forecast lead. Sunrise and sunset sit beside the Day & night heading; the duplicate date and explanatory footer are omitted. It stays on a full civil-day scale while the six-hour slider and autoplay move the sun/day or moon/night marker. Sunrise and sunset are approximate astronomical times for the canonical Hong Kong Observatory coordinates; they follow the selected forecast's Hong Kong date, including midnight rollover. The arc is illustrative rather than a true solar-elevation or cloud-cover prediction. `weather-solar.mjs` uses the locally vendored [SunCalc 2.1.1](https://github.com/mourner/suncalc) module in `assets/vendor/suncalc/`, with its BSD-2-Clause license alongside it. The dashboard loads as an ES module; it needs no additional weather API request. Tests cover Hong Kong versus UTC day boundaries, day/night states and the fixed time scale.

Local deployment sources live under `scripts/weather/gnn/`. On climet3, the runtime is `/workspace/wanghan/personal/weather/`, with the existing `han-fdn` Python environment. CLP code, checkpoints and frozen builds are read from their existing authorities and never copied into GitHub. Official past-day archives are cached in `personal/weather/archives`; live observations come from `HKO_API_ingestion`. API observations are already the calibration target domain and must not receive the historical HKO2025 correction a second time.

The existing CLP collector runs every ten minutes on climet3 and saves all seven raw feeds plus normalized station rows. GNN inference now runs hourly at minute 07 HKT, using the most recent complete 72-hour input window; its model origin remains aligned to :50. `run.sh` calls `forecast-expanded.py` on CPU and publishes `data/gnn.json`. `observations.sh` runs at minutes 03, 13, 23, 33, 43 and 53 HKT, exports the collector's ten-minute station temperatures, fetches the HKO report/local/daily products, archives a complete snapshot, and publishes `data/weather.json`. Source publication can lag the collection clock; original observation times are always retained.

Both publishers use `publish.sh` and a shared Git lock around the existing sparse `publish/` checkout. This prevents overlapping observation and GNN jobs from mixing their staged changes. Push conflicts rebase and retry. Runtime logs are `logs/run.log` and `logs/observations.log`; `install_schedule.py` replaces only these two jobs, preserves all other collectors, and backs up the previous crontab in `_tmp/`. Local deployment sources remain authoritative; the server is the authority for collected data.

The input window must have at least 90% timestamp coverage in each core feed and no network-wide gap longer than 60 minutes. Each published station-variable additionally needs 90% valid history and a reading within the last hour of the input window. These checks prevent the observed twelve-hour collector outage from being silently treated as normal station missingness. Inputs older than 30 minutes produce an unavailable state. Incomplete history produces a warming-up state with actual coverage; it does not publish predictions. Prior output survives unexpected inference errors, and the browser hides predictions after their final valid time. Historical replays are explicitly marked and rejected by the live UI.

Live verification after the cadence change produced a ready six-hour forecast with 100% core-feed timestamp coverage and no network-wide input gap. Earlier warming-up periods were caused by an interrupted collector; the coverage checks remain active.

Manual update: `bash /workspace/wanghan/personal/weather/run.sh`. A validation replay can use `forecast.py --origin 2026-10-26T23:50 --output /workspace/wanghan/personal/weather/_tmp/replay.json`; never publish that file as live. `node --test tests/gnn.test.mjs` covers lead timestamps, malformed output, replay rejection and expiry.

## Interface

The dashboard uses Source Sans 3 throughout, sentence-case headings and four text levels: 32px page title and current reading, 20px section headings, 16px body and primary controls, and 14px supporting text. Map attribution retains a compact 12px size. Shared navigation and themes follow [the design system](design.md). Spacing follows an 8px rhythm; dates, temperatures and station controls remain readable on mobile without shrinking their text.

All station markers remain available. Labels that would overlap are hidden at the current zoom, with the selected station taking priority; hovering, focusing or zooming reveals details. The station selector provides access to every point. Numeric labels and the legend use a traditional blue–white–red palette with contrasting black/white text. GNN color bounds span every lead of the selected variable and remain fixed during playback. Changing the layer or variable closes the previous popup so an observation cannot remain visible over an unavailable forecast layer.

When the GNN has insufficient observations, a prominent status states that no forecast is available. A meter shows the minimum reported input-feed coverage over the 72-hour window. This is data coverage, not task progress or an estimate of when forecasts will arrive. Variable and time controls appear only for a ready, unexpired forecast. The empty map remains smaller; official HKO forecasts remain readable alongside it.

The map uses temperature labels, clickable station details, a station selector and a reset view. Scrolling over the map zooms it; scrolling outside the map moves the page. Selecting a date updates the Hong Kong daily forecast below the map; it does not change the observation map into a forecast map. Desktop and mobile layouts follow the homepage's light and dark themes. The desktop weather page widens to 1280 px with a 540 px-high map on the left; the right sidebar stacks HKO local and daily forecasts. Daily dates use a three-column grid, followed by the selected day details. Mobile stacks the two columns. The interaction references are [Windy](https://www.windy.com/) (map, location selection and date browsing) and the [Observatory's regional forecast map](https://maps.weather.gov.hk/ocf/index_e.html) (numeric station labels and a time control).

`weather-stations.js` is the single coordinate source for 39 physical temperature stations (including the additional ten-minute feed stations). Coordinates and aliases are taken from the [official station table](https://www.hko.gov.hk/en/cis/stn.htm). Leaflet 1.9.4 uses MapLibre GL 5.6.1 with the 0.1.3 Leaflet adapter to render a key-free OpenFreeMap vector basemap. Adapter 0.0.22 only supported MapLibre 2–4 and left the basemap camera out of sync with markers when panning under MapLibre 5; 0.1.3 includes the v5 transform synchronization fix. `assets/weather-map-style.json` owns the green land, blue water, restrained road labels and hillshade styling, inspired by the MMLWP paper palette. Public AWS/Terrain Tiles (Terrarium encoding) supply the elevation shading; no peak icon layer is included. The map keeps © OpenStreetMap visible; a keyboard-accessible information disclosure contains OpenFreeMap, OpenMapTiles and the linked terrain sources. This is an independently styled open-data map, not the exact Mapbox paper style. No Mapbox token or Mapbox request is used. The previous Mapbox candidate was blocked before publication and replaced in its unpublished commit; do not allowlist that old secret-scanning alert. Only viewport tiles are fetched during interactive use, not through the scheduled workflow; ordinary browser caching is retained. A station selector remains usable if the map library or tiles are unavailable.

## Sources and timestamps

The updater retains three official English-language JSON products, without an API key:

- [Regional observations](https://data.weather.gov.hk/weatherAPI/opendata/weather.php?dataType=rhrread&lang=en): station temperatures and observation timestamps.
- [Local forecast](https://data.weather.gov.hk/weatherAPI/opendata/weather.php?dataType=flw&lang=en): the stated forecast period, narrative and outlook.
- [Nine-day forecast](https://data.weather.gov.hk/weatherAPI/opendata/weather.php?dataType=fnd&lang=en): forecasts keyed by their actual dates. The first entry may be tomorrow; it must not be relabeled as today.

The published snapshot retains the products unchanged under `current`, `localForecast` and `dailyForecast`. `fetchedAt` is the website retrieval time in UTC; source `updateTime` and observation `recordTime` remain separate. `schemaVersion` is 1 and `updateIntervalMinutes` is 10. `stationObservations` separately contains the actual ten-minute station temperatures, their per-station `recordTime`, and the source URL. The map prefers this block over the hourly report, retaining the report unchanged. `station-observations.py` reads the collector’s normalized CSV and maps the documented HK Park alias to Hong Kong Park. Missing temperatures are omitted, not replaced with zero. The UI displays times in Hong Kong time (UTC+8).

Missing values remain missing, not zero. Relative humidity in this product belongs to the Observatory station and must not be assigned to every temperature station. Rainfall districts and temperature stations are different location sets. The [official API documentation](https://data.weather.gov.hk/weatherAPI/doc/HKO_Open_Data_API_Documentation.pdf) describes these products; the [open-data catalogue](https://www.hko.gov.hk/en/abouthko/opendata_intro.htm) lists their publication frequencies. Source products can update more often than this website retrieves them.

## Publishing and local archive

climet3 is the automatic publishing authority. The website reads the latest `data/weather.json` and `data/gnn.json` from the independent `weather-data` GitHub branch. Data updates do not require a Pages build. `.github/workflows/update-weather.yml` is retained only as a manual emergency fallback for the three JSON products, without a schedule or push trigger. That fallback lacks the server's ten-minute station block; do not mistake its hourly report for ten-minute measurements.

An open weather page polls the published files every ten minutes while visible and refreshes if overdue on returning to the tab. Manual refresh remains available. The local `data/weather.json` is a fallback with its actual dates. Failed requests retain the previous good snapshot; timestamps older than six hours continue to trigger the existing stale-data warning. HKO local/daily forecast issuance remains at the official cadence, independently of our polling.

`data/weather-archive/` is the Windows-side archive and is gitignored. It is not published to GitHub Pages:

- `hko-api/raw/YYYY/MM/DD/`: original temperature, humidity, pressure, wind, solar radiation, visibility and hourly-rainfall responses, named by UTC fetch time.
- `hko-api/processed/YYYY/MM/DD/`: normalized rows with fetch time, observation time, source, station, variable, value and unit.
- `hko-api/historical_packages/` and `hko-api/derived/`: the existing downloaded historical packages and derived tables.
- `hko-api/latest/`: the collector's current complete data and acquisition status.
- `website-archives/YYYYMM/`: past-day HKO archive packages used by the GNN.
- `website-archives/website/YYYY-MM-DD/`: complete website snapshots for every successful website collection, including unchanged source report products and the ten-minute station block. Archive dates and filenames are UTC; source HKT timestamps are retained inside.
- `last-sync.json` and `sync.log`: the most recent completed local synchronization and operational log.

`scripts/weather/sync-archive.py` pulls from `/workspace/wanghan/data/HKO_API_ingestion/` and `/workspace/wanghan/personal/weather/archives/` using `ssh climet3` and tar. It skips the server's documentation symlink, compares ordinary file size and modification time, transfers only new/changed files, and never deletes remote or local history. A failed transfer is retried by the next run. Previously downloaded files remain intact.

The Windows scheduled task **Personal Weather Archive Sync** runs every ten minutes using `pythonw.exe`, without a console window. `scripts/weather/install-archive-task.ps1` installs or updates it for the current logged-in user with overlapping scheduled runs disabled. The computer must be awake, the user logged in, and climet3 reachable. The server continues collecting during local downtime; the next successful sync catches up all retained files. This task is unrelated to Gallery, for which automatic synchronization remains disabled.

Manual catch-up: `./scripts/manage.ps1 weather-sync`. Check `data/weather-archive/last-sync.json` and the scheduled task's last result. The first copy includes roughly 1.35 GB of existing collected data; subsequent transfers are incremental. Raw historical gaps from before collection are not fabricated or guaranteed recoverable.

## Local development

Local development uses Node.js 24 or later. The climet3 updater uses the verified `/usr/local/bin/node` (18.20.8, supporting fetch and AbortSignal.timeout); no npm dependencies are required.

```sh
node scripts/weather/update-weather.mjs
node --test tests/update-weather.test.mjs
```

The updater resolves its default output to `data/weather.json` inside this repository, even when launched from another working directory. Use `--output /absolute/path/weather.json` for a scratch snapshot. The tests cover missing observations, invalid dates, upstream HTTP/JSON failures, distinct source times, and preservation of the previous file on failure.
